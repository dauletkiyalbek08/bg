# Устройство Bagdar

`app/page.tsx` передаёт клиенту только признак допустимости демо. Весь персональный state приходит через динамический `/api/state` после проверки непрозрачной серверной сессии. Отчёты и JSON получают `Cache-Control: private, no-store`.

`app/api/[...path]/route.ts` — HTTP-граница: origin, входные схемы, cookie, ограничения частоты, импорт, файлы, PDF и Excel. `lib/service.ts` — права и предметные операции. `lib/store.ts` — SQLite/Supabase, ревизии, атомарная фиксация, последовательность локальных запросов и компенсация создания Auth-аккаунта при ошибке записи. Supabase и Auth не являются одной распределённой транзакцией: отмена внешнего создания — best effort; при её отказе необходима сверка.

## Области данных

- Общие вопросы/профессии имеют `org=null`.
- Аккаунты платформы не принадлежат школе; организация есть у всех школьных ролей.
- Ученик получает только себя и свои попытки, результаты, анкету и избранное, а также занятия своего класса.
- Руководитель получает учеников текущих назначенных классов, результаты и прогресс. Сырые ответы и личные свободные поля анкеты исключаются на сервере.
- Специалист получает данные своей организации.
- Администратор платформы получает организации и аккаунты специалистов; персональные ответы учеников ему не выдаются.
- Внутренние комментарии не включаются в API ученика/PDF.

На изменение данных проверяются роль, организация, действующий статус, необходимость смены пароля и дополнительные условия конкретной операции. Роль и организация не берутся из клиентских metadata. Пароль, хеш и cookie не включаются в state. RLS таблицы Supabase закрывает прямой доступ; привилегированный ключ используется только на сервере.

## Согласованность

SQLite фиксирует набор изменений в `BEGIN IMMEDIATE` с проверкой ожидаемых ревизий. Supabase RPC делает то же в PostgreSQL с транзакционной блокировкой. В PostgreSQL есть уникальный логин, уникальная активная попытка назначения/ученика, внешняя ссылка на организацию и отложенные проверки владельца/класса/назначения. Локальные предметные ограничения дополнительно проверяются сервисом.

Начало повторно возвращает незавершённую попытку. Сохранение ответа требует текущую версию; конфликт не затирает другие вкладки. Завершение повторно возвращает сохранённый результат и не допускает пропуски. Квоты и ограничения организации повторно проверяются на сервере. Изменение лимита/создание ученика затрагивает запись организации, чтобы конфликтующие операции не обходили лимит.

## Контент и сохранённые результаты

В попытке сохраняются текст/версия каждого вопроса, набор шкал, порядок и версия анкеты. В результате сохраняются баллы, методика, объяснения, компоненты и пять рекомендаций. Редактирование банка/каталога применяется к будущим вычислениям; сохранённый результат не пересчитывается при чтении.

## Локальное хранение

На диске остаются SQLite и приватные материалы; процессы и открытые соединения после восстановления среды нужно запускать заново. Содержимое `.data/` не включается в git. Для резервной копии работающей SQLite используйте её backup API или останавливайте сервер перед копированием, учитывая WAL; простое копирование одного `.sqlite` во время записи не гарантирует полную копию.

В Supabase материалы находятся в private bucket; сервер после проверки выдаёт URL на 60 секунд. В локальном режиме материал читается только через защищённый endpoint и выдаётся как attachment. Выполняемые типы/HTML/SVG не принимаются. Полная антивирусная проверка содержимого не заявляется.

## Netlify demo adapter

На Netlify вместо файловой SQLite используется приватный site-wide Blobs store с сильной согласованностью. Каждый экземпляр Store читает один снимок документа и его ETag; commit формирует новый снимок и записывает его с `onlyIfMatch`, а первоначальная запись — с `onlyIfNew`. Если параллельная функция успела изменить базу, весь запрос отклоняется, включая сопутствующие записи. Ревизии предметных сущностей продолжают проверяться. Локальное поведение и код разграничения доступа остаются общими для всех адаптеров.

Материалы Netlify хранятся отдельными Blob-объектами и выдаются через авторизованный HTTP-обработчик. Публичных адресов хранилища не формируется. Копии исходной `.data` и открытые локальные пароли при публикации не переносятся. Установка Netlify-сайта создаёт новое синтетическое демо.
