# Bagdar

Локальная работающая версия портала профориентации с интерфейсом на казахском языке. Next.js 16, React 19, TypeScript, Motion, Recharts. Демо сохраняет состояние в SQLite; это отдельный режим с синтетическими данными, а не рабочая база школьников.

## Запуск

Нужен Node.js 24.19.0 (версия закреплена в `.nvmrc`). Команды из корня репозитория:

```sh
npm ci
BAGDAR_MODE=demo npm run seed
BAGDAR_MODE=demo npm run dev
```

Откройте приложение на порту 3000 средствами вашей среды. На странице входа есть «Демо кіру»: ученик, руководитель класса и специалист. Публичной регистрации нет.

Для собранной версии:

```sh
BAGDAR_MODE=demo npm run build
BAGDAR_MODE=demo npm start
```

Чтобы запустить на другом порту, добавьте `-- --port 3002`. Режим `demo` нужно указывать и при запуске собранного приложения. `.env.example` описывает доступные настройки; при желании скопируйте его в игнорируемый `.env.local`. Скрипты seed читают этот файл через загрузчик Next.js.

Каждая облачная задача уже изолирована: используйте существующий checkout, не создавайте отдельный Git worktree без запроса пользователя.

## Что работает

- Четыре роли, независимые организации, статусы подписки, лимиты активных учеников.
- Вход по логину/паролю, серверная сессия с HttpOnly-cookie, хеширование scrypt в демо, блокировка и отзыв сессий, обязательная смена временного пароля.
- Создание организаций, специалистов, руководителей, учеников и классов. Выдача временного пароля однократно; повторная печать старого пароля невозможна.
- 12 полей анкеты, черновик с автосохранением, разграничение личного вопроса и структурированных ответов.
- Назначение теста классу, всем ученикам или отдельному ученику; срок, повторное прохождение, сохранение прогресса, защита от конфликтов вкладок.
- 300 авторских вопросов: 108 по интересам, 96 по направлениям Климова, 96 по самооценке навыков. В каждой попытке 36 сбалансированных вопросов.
- Серверный расчёт, две радар-диаграммы, уровни самооценки, пять профессий с объяснениями, сохранённая версия результата, сигналы качества ответов.
- 100 профессий: поиск, фильтры, избранное, карточки, пути обучения. Нет выдуманных названий вузов, грантов и зарплат.
- Общие и локальные вопросы/профессии, создание и редактирование в пределах роли. Попытка содержит снимок вопросов; старый результат не изменяется при редактировании каталога.
- Кабинет руководителя с доступом только к своим классам; комментарии для ученика или только сотрудников.
- Аналитика по назначению и классу; распределения скрываются для групп менее пяти завершённых результатов. Excel-экспорт в пределах прав.
- Импорт учеников CSV/XLSX: предпросмотр, ошибки строк, проверки логинов, лимитов и классов, запрет формул и ограничение распаковки XLSX. Локальный импорт атомарен; повтор запроса с тем же ключом не создаёт аккаунты заново.
- Занятия, отмена, посещаемость, обратная связь после занятия, HTTPS-ссылки и приватные файлы PDF/PNG/JPEG/WebP до 20 МБ, до 10 на занятие.
- PDF-отчёт с внедрённым шрифтом для казахских букв, числовыми шкалами, графическими полосами, рекомендациями и пояснением ограничений.
- Адаптивный интерфейс, светлая/тёмная/системная тема, клавиатурная навигация и reduced motion.

## Данные демо и администратор

Первое обращение к API или `npm run seed` создаёт две независимые синтетические организации. В основной — классы 9 «А» и 10 «Б», шесть учеников, четыре завершённых результата, одно прошедшее и два будущих занятия. Повторный seed не дублирует записи и не сбрасывает пароли.

Файлы в `.data/` исключены из Git:

- `bagdar.sqlite` и файлы WAL/SHM — база;
- `materials/` — приватные локальные вложения;
- `demo-credentials.json` — сгенерированные локальные пароли начальных демоаккаунтов, права файла 0600.

Вход без пароля доступен только фиксированному списку синтетических демоаккаунтов и только в локальном деморежиме. Он отключён при `BAGDAR_BACKEND=supabase`. Для просмотра кабинета администратора платформы используйте логин `superadmin` и соответствующий пароль из локального файла. Не публикуйте файл паролей и не используйте эти аккаунты с реальными данными.

Пароли новых аккаунтов показываются только в ответе создания/сброса и не добавляются в этот файл. Сохранение/печать выполняются из открытого диалога. Потеря этого ответа требует нового сброса.

`BAGDAR_DATA_DIR` позволяет выбрать отдельный каталог, например для независимого демо. Не удаляйте существующий каталог для «исправления» проблем: он содержит сохранённую работу.

## Проверки

```sh
npm run lint
npm run typecheck
npm test
npm run test:e2e
BAGDAR_MODE=demo npm run build
```

Unit/integration-проверки запускаются без внешних ключей. PostgreSQL-тесты используют PGlite: выполняют настоящую миграцию, проверяют запрет прямого доступа, CAS-конфликты, уникальность логина и межорганизационные ссылки. Это не проверка удалённого Supabase.

E2E использует Chromium по `/usr/bin/chromium`. Если он установлен в другом месте, задайте `CHROMIUM_PATH`. Тест поднимает отдельный сервер на порту 3001 и создаёт новый каталог `.data/e2e-*`; основная демобаза не меняется. Не запускайте два `next dev` в одном checkout одновременно: Next.js блокирует общий каталог разработки. Для E2E остановите обычный dev-сервер. После E2E можно запускать основной сервер снова.

Браузерные проверки проходят полный путь ученика, PDF, импорт, комментарии, экспорт, приватные материалы, посещаемость, обратную связь, создание аккаунтов и смену пароля, разные роли/организации, остановку подписки и блокировку активной сессии. Скриншоты и trace сохраняются в игнорируемом `test-results/`.

## Расчёт

Код — `lib/scoring.ts`, содержание — `lib/content.ts`.

Каждая шкала нормализуется отдельно: `100 × mean((ответ − 1) / 4)`; для обратного вопроса используется `1 − нормализованный ответ`. Две дополнительные позиции Климова распределяются с учётом предыдущих попыток. При повторе сначала используются новые вопросы; при исчерпании банка допускаются старые.

Подбор: 50% сходства профиля интересов, 25% направлений Климова, 25% самооценки навыков; бонус структурированных предпочтений от 0 до 5. Сходство семейства равно `100 − средняя абсолютная разница` между ответами и целевым профилем профессии. Тексты объяснений основаны на сохранённых компонентах. Крайние значения, пропуски, обратное кодирование и воспроизводимость покрыты тестами.

Это авторская исследовательская анкета, а не валидированный психологический инструмент. Вопросы сформированы из тематических действий и контекстов; целевые профили профессий — начальные модели. Для реальных рекомендаций необходимы содержательная редактура, методическая экспертиза и пилотирование.

## Supabase — подготовленный, но не проверенный удалённо режим

По выбору владельца эта среда остаётся на локальной демобазе. В коде есть дополнительный адаптер Supabase Auth + PostgreSQL + private Storage, миграции и bootstrap-команда. Он не объявляется готовым к реальным школьникам без отдельной проверки с проектом владельца.

Порядок будущего подключения:

1. Создать отдельный проект Supabase в согласованном регионе.
2. Выполнить `supabase/migrations/001_bagdar.sql` и `002_private_storage.sql` в новом проекте. Не применять миграции вслепую к существующим данным.
3. В настройках Auth отключить публичную регистрацию. Это настройка Supabase, а не просто отсутствие кнопки в интерфейсе.
4. Задать через защищённые настройки окружения `BAGDAR_BACKEND=supabase`, `BAGDAR_MODE=private`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `BAGDAR_APP_ORIGIN`.
5. `npm run seed` добавляет общий контент без демоаккаунтов. Для первого администратора временно задать `BAGDAR_BOOTSTRAP_LOGIN` и `BAGDAR_BOOTSTRAP_PASSWORD` (16+ символов) и выполнить `npm run seed:bootstrap`, затем убрать bootstrap-пароль из окружения.
6. Повторить проверки Auth, приватных файлов, блокировок и доступа всех ролей на проекте. Только после этого рассматривать размещение на Vercel.

Служебный email на `.invalid` используется только как внутренний идентификатор Auth; ученикам не нужна почта.

Модель первой версии — типизированные документы в приватной таблице `bagdar_records` с ревизиями и атомарным RPC. RLS и grants запрещают весь прямой доступ anon/authenticated; приложение обращается к базе серверным ключом, а роль, организация, класс и видимость проверяются в `lib/service.ts`. Ключ не передаётся браузеру. RPC дополнительно проверяет роль service_role и ожидаемые ревизии. Это серверная архитектура, а не разрешение клиенту читать общую таблицу с фильтром.

При масштабировании следует заменить загрузку коллекций в `getState` выборками по области доступа с серверной пагинацией и перейти к предметным нормализованным таблицам. Текущая версия рассчитана на демонстрацию и разработку; производительность на 1000+ учениках не заявляется.

## Границы текущей версии

Полное исходное задание находится в `docs/SPECIFICATION.md`; оно описывает целевой продукт, а не список уже пройденных проверок. Дополнительно к проверке удалённого Supabase остаются:

- устойчивый возобновляемый массовый импорт в Supabase Auth (в этом режиме массовый импорт явно отключён; отдельное создание аккаунтов подготовлено);
- импорт руководителей, редактирование схемы анкеты и произвольный конструктор опросов после занятия;
- загрузка офисных файлов как материалов (XLSX разрешён для импорта; материалы — только PDF/изображения);
- централизованная очистка по утверждённым срокам хранения, обработка запросов удаления и проверка резервного восстановления;
- окончательная языковая/методическая экспертиза контента и проверка всех требований WCAG;
- production-наблюдаемость и распределённый rate limit: текущие ограничения частоты рассчитаны на один локальный процесс.

Юридическое основание обработки данных несовершеннолетних, согласия представителей, сроки хранения и регион базы требуют решения владельца перед использованием реальных данных. Оплата, родительский кабинет, внешние ИИ-сервисы и сведения об экзаменах не реализуются.

## Развёртывание демо на Netlify

[Развернуть Bagdar на Netlify](https://app.netlify.com/start/deploy?repository=https://github.com/dauletkiyalbek08/bg)

Это ссылка на мастер создания сайта, а не адрес уже опубликованного приложения. Войдите в Netlify и разрешите подключение выбранного GitHub-репозитория. Фактический адрес `*.netlify.app` выдаёт Netlify после успешной сборки.

`netlify.toml` закрепляет адаптер Next.js, сборочную команду и шрифт PDF. При сборке на Netlify приложение автоматически использует **Netlify Blobs** для демобазы, сессий и материалов. Локальная разработка продолжает использовать SQLite; переключение не переносит локальные данные в публичное демо.

Первое обращение к API создаёт отдельные синтетические данные в site-wide store `bagdar-demo-v1`. Они переживают перезапуск функций и новые deploy того же сайта. Вложения находятся в отдельном приватном store. База записывается одним документом с strong consistency и условным ETag: конфликтующие запросы получают ошибку, а не затирают изменения молча. Это решение для небольшого демо, не замена полноценной производственной базе.

В Netlify не создаётся локальный файл открытых демопаролей. Для знакомства используйте кнопки «Демо кіру»; в публичном демо нет кнопки входа супер-администратора. Не вводите реальные данные учеников. Поскольку демонстрационные аккаунты общие, изменения в них видны другим посетителям этого демосайта.

Внешние ключи для Netlify Blobs приложение не запрашивает: Netlify предоставляет runtime-контекст своему серверному коду. `NETLIFY_AUTH_TOKEN` нужен только если поручить агенту публикацию через Netlify CLI/API; для ручного мастера по ссылке он не нужен. Токен вводится только в защищённых настройках среды и не передаётся в репозиторий или браузер.

Проверка адаптера: `npm run test:netlify`. Четыре сценария выполняются с официальным локальным BlobsServer: инициализация, отдельные экземпляры хранилища, конфликт ETag без частичной записи и материалы. Локальный эмулятор 11.1.7 не возвращает ETag в GET; тестовый транспорт получает тот же ETag из его LIST. Реальный SDK и проверка условного PUT остаются включены. Проверки не считаются валидацией опубликованного сайта.
